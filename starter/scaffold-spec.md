# Scaffold specification

*This is the specification learners hand to Claude Code in phase 1. It is deliberately
prescriptive: every learner must end up with substantially the same project, because phases 2
onward assume a known starting point. If two learners' scaffolds differ in the names below,
later phases get harder to support.*

---

## Goal

A minimal, working Django REST Framework project with a passing test suite. No authentication
features of any kind — those are built later, through the spec-driven workflow.

## Required names

These are not suggestions. Later phases refer to them.

| Thing | Value |
|---|---|
| Django project | `sdd_django_demo` |
| Django app | `api` |
| Settings module | `sdd_django_demo.settings` |
| Health endpoint | `GET /api/health/` |
| OpenAPI schema | `GET /api/schema/` |
| Swagger UI | `GET /api/docs/` |

## Dependencies

Install the current stable release of each, and pin the exact versions in `requirements.txt`
with a comment recording the date they were resolved:

- `Django`
- `djangorestframework`
- `drf-spectacular`
- `pytest`
- `pytest-django`

Use a virtual environment at `.venv/`.

## Required behaviour

1. `GET /api/health/` returns HTTP 200 with the JSON body `{"status": "ok"}`.
2. The project runs on SQLite with default settings. No environment variables are required to
   run it or its tests.
3. `pytest` discovers and runs tests, configured through `pytest.ini` (or `pyproject.toml`)
   with `DJANGO_SETTINGS_MODULE` set correctly.
4. There is exactly one test, covering the health endpoint: it asserts the 200 status and the
   response body.
5. `GET /api/schema/` returns the OpenAPI schema for the project, generated by `drf-spectacular`.
6. `GET /api/docs/` serves an interactive Swagger UI backed by that schema.

## Repository furniture

Copy `starter/pull_request_template.md` to `.github/pull_request_template.md` in
the learner's repository. GitHub uses it for every pull request they open, which is what puts a
plan into each PR description without anyone having to remember.

## Explicitly out of scope

Do not add: user registration, login, authentication, permissions, JWT, custom user models,
serializers beyond what the health endpoint needs, Docker, environment-variable configuration,
or a production settings split. The scaffold is a starting line, not a head start.

## Acceptance checks

The learner must be able to run all four and see the stated result:

```bash
.venv/bin/python manage.py check          # → System check identified no issues
.venv/bin/python manage.py migrate        # → applies without error
.venv/bin/pytest                          # → 1 passed
.venv/bin/python manage.py runserver      # → GET /api/health/ returns {"status": "ok"}
```

With the server running, both of these must work in a browser:

- `http://127.0.0.1:8000/api/docs/` renders Swagger UI and lists the health endpoint
- `http://127.0.0.1:8000/api/schema/` returns the raw OpenAPI document

**The last two checks are not decoration.** This scaffold was built and verified on Django 6.1
and Python 3.14 on 19 August 2026, and during that build `manage.py check` reported no issues and
`pytest` passed **while `INSTALLED_APPS` was still missing `rest_framework`, `drf_spectacular` and
the app itself**. A DRF function view and a URL route both work without the apps being installed;
only requesting `/api/docs/` exposed it, with a 500.

A green suite is not proof the project is configured. Run all four.
