## Context

See proposal.md - Why. Relevant current state:

- `drf-spectacular` is already installed and wired up: `GET /api/schema/` serves the OpenAPI 3
  schema for every DRF view, and each view already gets an `operationId` from drf-spectacular's
  defaults (derived from the view name) without any extra annotation work having been done for
  this change.
- There is no `.github/workflows/` directory anywhere in this repo yet - this change adds the
  first GitHub Actions workflow.
- `openspec/specs/` holds three canonical capability specs today (`user-signup`, `user-signin`,
  `user-password-reset`); `embargo` has a delta spec in `openspec/changes/add-embargo/` but no
  route of its own - its rules are invoked from inside signup/signin, not exposed as a separate
  endpoint, so it has nothing for this pipeline to hit directly.
- This project already has a requirement -> code -> test traceability convention
  (`traceability.md` per change) and a blocking/non-blocking review contract used by
  `/code-review` (`openspec/config.yaml` - `operations.apply.guidance`). Both are reused here
  rather than inventing a parallel convention.

## Goals / Non-Goals

**Goals:**
- Satisfy every requirement in `specs/api-behavior-verification/spec.md` with tooling that treats
  OpenAPI, the OpenSpec specs, Postman/Newman, and Claude as separate, single-purpose stages (see
  proposal.md and issue #38 for why the split matters).
- Make adding a new endpoint's behavioural coverage a matter of adding one assertions-library
  entry, never a collection edit.

**Non-Goals:**
- Not a replacement for `pytest` - `pytest` still verifies behaviour against the Django code
  in-process; this pipeline verifies the deployed HTTP surface from outside, after merge.
- Not full response-schema validation against the OpenAPI schema (e.g. exhaustive
  type/format checking of every field) - assertions are scoped to what the OpenSpec requirements
  actually state. A generic schema-conformance check can be layered on later without changing this
  design.
- Not a mechanism for testing `embargo` directly - it has no endpoint of its own today (see
  Context). Its behaviour is exercised indirectly through whichever signup/signin assertions
  already cover the requests it affects.

## Decisions

**Derive the collection from a schema file generated by `manage.py spectacular`, not by scraping
a live server.** `python manage.py spectacular --file schema.json` (drf-spectacular's own
management command) produces the same OpenAPI document `/api/schema/` serves, but as a build
artifact the CI job can generate before the server needs to be up - decoupling "what endpoints
exist" from "is the server currently running." Alternative considered: fetch `/api/schema/` from
the already-started dev server - rejected, since it makes collection generation depend on server
startup timing for no benefit.

**Convert schema to collection with `openapi-to-postmanv2` (Postman's own converter), execute
with Newman (Postman's own CLI runner).** Both are maintained by Postman, widely used for exactly
this OpenAPI -> Postman -> CI pipeline shape, and avoid hand-writing a converter. They're CI-only
Node dependencies, isolated from the Django project's own `requirements.txt`.

**Assertions live in one checked-in library, keyed by OpenAPI `operationId`, not inside the
generated collection.** Each entry: the requirement id(s) it verifies, and one or more Postman
test-script snippets (`pm.test(...)`) to attach to that operation's request(s). A separate merge
script (`postman/merge_assertions.js`, using the `postman-collection` SDK) reads the generated
collection and the assertions library and writes each matching entry's scripts into that request's
`event: test` array; a request whose `operationId` has no library entry keeps only a default
`pm.test('status code is successful', ...)` added during the same merge pass. This is what makes
"derive coverage from OpenAPI" and "judge correctness from the specs" two genuinely independent
inputs that only combine at merge time, rather than one hand-maintained file doing both jobs -
directly satisfying *Judge behaviour against the OpenSpec specs* and *Derive endpoint coverage
from the OpenAPI schema* as separate requirements.

**Run the merged collection against a real `runserver` instance in the CI job, not against
mocks.** The spec's *Execute checks with Postman tooling* and *Fail the run on an assertion
failure* requirements are about the API's real HTTP behaviour, which a mocked server can't
provide. The CI job runs `migrate`, starts `runserver` in the background, polls `GET
/api/health/` until it responds, then runs Newman with a JSON reporter
(`newman run collection.json --reporters cli,json --reporter-json-export result.json`).

**Claude review is a scripted Anthropic API call, not an interactive session.** A small script
(`postman/review_with_claude.py`) sends the merged collection, `result.json`, and the contents of
`openspec/specs/**/spec.md` to a Claude model via the Messages API, with a prompt that mirrors
`/code-review`'s contract (`openspec/config.yaml`) - a finding blocks only if it cites a
requirement id, a specific failing assertion, or a documented convention - and asks for a
structured JSON verdict: `{"findings": [{"requirement": "...", "detail": "...", "blocking":
true|false}], "ready": true|false}`. The workflow step parses that JSON; `ready: false` or any
`blocking: true` finding fails the job, satisfying *Fail the run on a blocking evaluation
finding*. A script call (rather than driving the interactive `claude` CLI) is chosen because CI
needs a single deterministic exit code from a non-interactive process, and the review here is one
bounded prompt with structured output, not a multi-step agentic task.

**Requirement/endpoint names in failure output come straight from the assertions library and the
Claude verdict JSON**, not from parsing Newman's own free-text output - Newman's `result.json`
already carries the assertion name (set to the requirement id or "default status check" at merge
time), so the workflow step just re-prints failing assertion names and blocking finding entries
verbatim, satisfying *Report which requirement failed* without extra parsing logic.

## Risks / Trade-offs

- [Claude API cost and latency on every push to `main`] -> the review call is small (a Postman
  collection, a JSON result file, and the specs directory, all well under typical context limits
  for this project's size) and runs once per push, not per request; acceptable for a demonstration
  project. Revisit batching or a cheaper model if the specs/collection grow substantially.
- [A live `runserver` in CI is heavier than pytest's in-process test client] -> deliberate: this
  pipeline exists specifically to check the deployed HTTP surface, which an in-process client
  can't do. SQLite and no required environment variables (per project context) keep the server
  trivial to start.
- [The assertions library can drift out of sync with the specs the same way hand-written tests
  could] -> mitigated, not eliminated, by the Claude evaluation step, whose whole job is to catch
  exactly that drift (missing or incorrect assertions) before it passes silently.
- [A request with no assertions-library entry is usually the unmodified base item the converter
  generated, whose body is an auto-generated placeholder example (e.g. `"string"` for a
  password) - a real endpoint has no reason to accept it] -> discovered during implementation:
  the default check originally asserted 2xx, which produced false failures on exactly these
  items (signup/signin/reset-confirm all correctly rejected their placeholder bodies). Lowered
  the bar to "no unhandled server error (< 500)" - still catches a crash, no longer assumes
  success for data nobody claimed was valid.
- [`operationId` is the join key between the assertions library and the collection, so a
  drf-spectacular default `operationId` change would silently orphan an assertions entry] -> the
  evaluation step's *missing coverage* check catches an orphaned entry as a requirement with no
  matching assertion in the merged collection, surfacing the drift rather than passing silently.
