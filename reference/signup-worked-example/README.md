# Worked example — user signup

A complete feature carried through spec-driven development, end to end. Every artefact here was
generated by the workflow you are about to run, in order, and the result was verified: 20 tests
passing, all fifteen requirements traced, three requirements broken deliberately to prove the
suite can fail.

**Read this before phase 2.** Not to copy it — you are building a different feature — but so you
know what each artefact is supposed to look like when it is right.

## What to read, in what order

| File | What it is | What to notice |

| [`spec/traceability.md`](spec/traceability.md) | The audit | Every `FR-` to its task, code line and test — plus what the table exposed |

## The four things this example is here to show you

**1. A requirement either can be tested or it cannot.**

Compare these two, both about the same behaviour:

> *"Passwords should be secure."*

> **FR-008**: The system MUST reject a password shorter than 8 characters. No character-class
> composition rules apply.

The first cannot fail a test, so it cannot be verified, so it is not a requirement — it is a
hope. Telling these apart on sight is the single skill this exercise exists to teach.

**2. The specification says nothing about Django.**

Read `spec/spec.md` and try to find a serializer, a view, a model or a status code framework.
There are none. "Returns HTTP 201" is in there because that is observable behaviour a client
depends on; *how* it is produced is not. The moment implementation detail enters a specification,
the specification stops being reviewable by anyone who does not already know the codebase.

**3. Tasks do not map to requirements, and that is the point of phase 5.**

`tasks.md` labels every task `[US1]` or `[US2]`. Nothing in it says `T003` satisfies `FR-008`.
The traceability table is built by hand, by reading both — and building it is what surfaced that
`T001` alone carries four requirements, which no reading of `tasks.md` alone would reveal.

**4. A green suite proves nothing until you have seen it go red.**

The bottom of `traceability.md` records three deliberate breaks and which test caught each. That
section is the difference between "the tests pass" and "the tests work". You will do the same to
your own suite in phase 9.

## What is deliberately imperfect

**FR-001 overlaps FR-002, FR-003 and FR-004.** "Accepts a username, email and password" and
"rejects a submission where the username is absent" are two views of one behaviour, which is why
they collapse into a single task. Would you have written it that way? Phase 3 asks you to
critique a specification — practise on this one first.

**The Assumptions section makes four decisions nobody asked for.** No email verification, no
token issued, usernames case-sensitive, signup open to anyone. Each is defensible and each was
invented, not specified. Finding invented detail is the skill phase 2 step 4 is training.

## Running it

The code here is extracted for reading and will not run on its own — it is the `api/` app of a
Django project built to `starter/scaffold-spec.md`. Build that scaffold in phase 1 and your
project will have the same shape.
