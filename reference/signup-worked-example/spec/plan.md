# Implementation Plan: User Signup

**Branch**: `feature/signup` | **Date**: 2026-08-19 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-user-signup/spec.md`

## Summary

Add a single write endpoint that accepts a username, an email address and a password, validates
all three, and creates exactly one account. Validation failures return a client error naming the
offending field; success returns 201. The stored password is not recoverable and never appears in
a response.

would add a settings change and an import path for no benefit.

## Design decisions

**No new model.** Django's built-in `User` already carries a unique username, an email field and
a hashed password. FR-006 (unique username) is enforced by the existing model; FR-007 and FR-014
(unique email, case-insensitive) are not, and must be enforced in validation.

**Validation lives in a serializer, not the view.** FR-002 through FR-008, FR-012 and FR-014 are
all field-level statements, and DRF serializers already produce field-keyed error responses,
which is exactly the shape FR-012 requires.

**Password storage is delegated.** FR-010 is satisfied by creating the user through Django's
`create_user`, which applies the configured hasher. Nothing here implements hashing.

**Password exclusion is explicit.** FR-011 requires the password never appear in a response, so
the response is built from an output representation that has no password field at all, rather
than from the input serializer with the field suppressed.
